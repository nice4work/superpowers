# 接收代码审查

## 概述

代码审查需要技术评估，而非情感表演。

**核心原则：** 实施前先验证。先询问再假设。技术正确性高于社交舒适度。

## 响应模式

```
当接收代码审查反馈时：

1. 阅读：完整阅读反馈，不做反应
2. 理解：用自己的话重述需求（或询问）
3. 验证：对照代码库实际情况检查
4. 评估：对此代码库技术上是否合理？
5. 响应：技术确认或理性的反驳
6. 实施：一次一项，每项都测试
```

## 禁止的响应

**绝不：**
- "你说得完全正确！"（明确违反指令文件）
- "好观点！"/"出色的反馈！"（表演性的）
- "让我现在实施"（在验证之前）

**替代：**
- 重述技术需求
- 提出澄清问题
- 如果错了就用技术推理反驳
- 直接开始工作（行动胜于言语）

## 处理不清晰的反馈

```
如果有任何项不清楚：
  停止 - 不要实施任何东西
  询问不清楚的项的澄清

原因：项目可能相关。部分理解 = 错误实现。
```

**示例：**
```
你的用户："修复 1-6 项"
你理解 1,2,3,6。对 4,5 不清楚。

❌ 错误：现在实施 1,2,3,6，稍后询问 4,5
✅ 正确："我理解第 1,2,3,6 项。在继续之前需要第 4 和第 5 项的澄清。"
```

## 来源特定处理

### 来自你的用户
- **可信** - 理解后实施
- **范围不清楚仍然询问**
- **不进行表演性同意**
- **跳到行动**或技术确认

### 来自外部审查者
```
在实施之前：
  1. 检查：对此代码库技术上是否正确？
  2. 检查：是否破坏现有功能？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上是否工作？
  5. 检查：审查者是否理解完整上下文？

如果建议似乎错误：
  用技术推理反驳

如果不能轻易验证：
  说出来："没有 [X] 我无法验证这一点。我应该 [调查/询问/继续] 吗？"

如果与你用户之前的决定冲突：
  先停下来与你的用户讨论
```

**你用户的规则：** "外部反馈——保持怀疑，但仔细检查"

## 对"专业"功能的 YAGNI 检查

```
如果审查者建议 "正确实现"：
  grep 代码库中的实际使用

  如果未使用："这个端点没有被调用。删除它（YAGNI）？"
  如果使用：那么正确实现
```

**你用户的规则：** "你和审查者都向我汇报。如果我们不需要这个功能，就不要添加。"

## 实施顺序

```
对于多项反馈：
  1. 首先澄清不清楚的内容
  2. 然后按此顺序实施：
     - 阻塞性问题（损坏、安全）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 单独测试每个修复
  4. 验证无回归
```

## 何时反驳

以下情况反驳：
- 建议破坏现有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对此技术栈技术上不正确
- 存在遗留/兼容性原因
- 与你用户的架构决定冲突

**如何反驳：**
- 使用技术推理，而非防御性
- 提出具体问题
- 引用工作的测试/代码
- 如果是架构性的，请你的用户介入

**如果你公开反驳感到不舒服：** 说出那种紧张感，然后告诉用户你看到的问题。他们会欣赏你的诚实。

## 确认正确的反馈

当反馈确实正确时：
```
✅ "已修复。[变更的简要描述]"
✅ "好发现 - [具体问题]。已在 [位置] 中修复。"
✅ [直接修复并在代码中展示]

❌ "你说得完全正确！"
❌ "好观点！"
❌ "谢谢你指出！"
❌ "谢谢 [任何]"
❌ 任何感谢表达
```

**为什么不感谢：** 行动说明一切。直接修复。代码本身就表明你听到了反馈。

**如果你发现自己即将写下"谢谢"：** 删掉它。改为陈述修复内容。

## 优雅地纠正你的反驳

如果你反驳了但错了：
```
✅ "你是对的 - 我检查了 [X]，它确实 [Y]。现在实施。"
✅ "验证了这一点，你是正确的。我最初的理解错了，因为 [原因]。正在修复。"

❌ 长篇道歉
❌ 为你为什么反驳辩护
❌ 过度解释
```

陈述纠正事实，然后继续。

## 常见错误

| 错误 | 修复 |
|---------|-----|
| 表演性同意 | 陈述需求或直接行动 |
| 盲目实施 | 先对照代码库验证 |
| 批量实施不测试 | 一次一项，每项都测试 |
| 假设审查者正确 | 检查是否破坏东西 |
| 避免反驳 | 技术正确性 > 舒适度 |
| 部分实施 | 先澄清所有项 |
| 无法验证仍继续 | 陈述限制，请求指导 |

## 真实示例

**表演性同意（差）：**
```
审查者："移除遗留代码"
❌ "你说得完全正确！让我移除那个..."
```

**技术验证（好）：**
```
审查者："移除遗留代码"
✅ "检查中... 构建目标是 10.15+，此 API 需要 13+。为了向后兼容需要保留遗留代码。当前实现有错误的 bundle ID——是修复它还是放弃 13 以下的支持？"
```

**YAGNI（好）：**
```
审查者："实现适当的指标跟踪，带数据库、日期过滤器、CSV 导出"
✅ "Grep 了代码库——没有东西调用这个端点。删除它（YAGNI）？还是有我遗漏的使用？"
```

**不清楚的项（好）：**
```
你的用户："修复 1-6 项"
你理解 1,2,3,6。对 4,5 不清楚。
✅ "理解 1,2,3,6。在实施之前需要第 4 和第 5 项的澄清。"
```

## GitHub 线程回复

在 GitHub 上回复内联审查评论时，在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为顶级 PR 评论。

## 底线

**外部反馈 = 要评估的建议，而非要遵循的命令。**

验证。质疑。然后实施。

不进行表演性同意。始终保持技术严谨。
