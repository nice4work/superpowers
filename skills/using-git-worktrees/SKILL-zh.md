# 使用 Git Worktrees

## 概述

确保工作在隔离的工作空间中进行。优先使用平台的原生工作树工具。仅在没有原生工具可用时才回退到手动 git worktree。

**核心原则：** 首先检测已有隔离。然后使用原生工具。然后回退到 git。永远不与宿主工具对抗。

**开始时宣布：** "我正在使用 using-git-worktrees 技能来设置隔离的工作空间。"

## 第 0 步：检测已有隔离

**在创建任何东西之前，检查你是否已在隔离的工作空间中。**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**子模块守护：** `GIT_DIR != GIT_COMMON` 在 git 子模块中也成立。在得出 "已在工作树中" 的结论之前，验证你不是在子模块中：

```bash
# 如果返回路径，你在子模块中而非工作树中——视为普通仓库
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**如果 `GIT_DIR != GIT_COMMON`（且不是子模块）：** 你已在一个链接的工作树中。跳到第 2 步（项目设置）。不要创建另一个工作树。

报告分支状态：
- 在分支上："已在隔离的工作空间中，位于 `<路径>`，分支 `<名称>`。"
- 分离 HEAD："已在隔离的工作空间中，位于 `<路径>`（分离 HEAD，外部管理）。完成时需要创建分支。"

**如果 `GIT_DIR == GIT_COMMON`（或在子模块中）：** 你在普通仓库检出中。

用户是否已在你的指令中表明了他们的工作树偏好？如果没有，在创建工作树之前征求同意：

> "你希望我设置一个隔离的工作树吗？它可以保护你当前的分支不受更改影响。"

尊重任何已声明的偏好而不询问。如果用户拒绝同意，原地工作并跳到第 2 步。

## 第 1 步：创建隔离的工作空间

**你有两种机制。按此顺序尝试。**

### 1a. 原生工作树工具（首选）

用户已要求隔离的工作空间（第 0 步同意）。你是否已经有创建工作树的方式？它可能是一个像 `EnterWorktree`、`WorktreeCreate`、`/worktree` 命令或 `--worktree` 标志的工具。如果你有，使用它并跳到第 2 步。

原生工具自动处理目录放置、分支创建和清理。当你有原生工具时使用 `git worktree add` 会创建宿主无法看到或管理的幽灵状态。

仅在没有原生工作树工具可用时才继续第 1b 步。

### 1b. Git Worktree 回退

**仅在 1a 不适用时使用**——你没有原生工作树工具可用。使用 git 手动创建工作树。

#### 目录选择

遵循此优先级顺序。明确的用户偏好始终优于观察到的文件系统状态。

1. **检查你的指令中是否有声明的工作树目录偏好。** 如果用户已经指定了一个，直接使用而不询问。

2. **检查已有的项目本地工作树目录：**
   ```bash
   ls -d .worktrees 2>/dev/null     # 首选（隐藏）
   ls -d worktrees 2>/dev/null      # 备选
   ```
   如果找到，使用它。如果两者都存在，`.worktrees` 优先。

3. **如果没有其他指导可用**，默认使用项目根目录下的 `.worktrees/`。

#### 安全验证（仅项目本地目录）

**在创建工作树之前必须验证目录被忽略：**

```bash
git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
```

**如果未被忽略：** 添加到 .gitignore，提交变更，然后继续。

**为什么关键：** 防止意外将工作树内容提交到仓库。

#### 创建工作树

```bash
# 根据选择的位置确定路径
path="$LOCATION/$BRANCH_NAME"

git worktree add "$path" -b "$BRANCH_NAME"
cd "$path"
```

**沙箱回退：** 如果 `git worktree add` 因权限错误失败（沙箱拒绝），告诉用户沙箱阻止了工作树创建，你改为在当前目录中工作。然后在原地运行设置和基线测试。

## 第 2 步：项目设置

自动检测并运行适当的设置：

```bash
# Node.js
if [ -f package.json ]; then npm install; fi

# Rust
if [ -f Cargo.toml ]; then cargo build; fi

# Python
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi

# Go
if [ -f go.mod ]; then go mod download; fi
```

## 第 3 步：验证干净基线

运行测试确保工作空间以干净状态启动：

```bash
# 使用项目适当的命令
npm test / cargo test / pytest / go test ./...
```

**如果测试失败：** 报告失败，询问是继续还是调查。

**如果测试通过：** 报告就绪。

### 报告

```
工作树就绪于 <完整路径>
测试通过（<N> 个测试，0 个失败）
准备实现 <功能名称>
```

## 快速参考

| 情况 | 行动 |
|-----------|--------|
| 已在链接的工作树中 | 跳过创建（第 0 步） |
| 在子模块中 | 视为普通仓库（第 0 步守护） |
| 原生工作树工具可用 | 使用它（第 1a 步） |
| 无原生工具 | Git worktree 回退（第 1b 步） |
| `.worktrees/` 存在 | 使用它（验证被忽略） |
| `worktrees/` 存在 | 使用它（验证被忽略） |
| 两者都存在 | 使用 `.worktrees/` |
| 两者都不存在 | 检查指令文件，然后默认 `.worktrees/` |
| 目录未被忽略 | 添加到 .gitignore + 提交 |
| 创建时权限错误 | 沙箱回退，原地工作 |
| 基线测试失败 | 报告失败 + 询问 |
| 无 package.json/Cargo.toml | 跳过依赖安装 |

## 常见错误

### 与宿主工具对抗

- **问题：** 当平台已提供隔离时使用 `git worktree add`
- **修复：** 第 0 步检测已有隔离。第 1a 步遵从原生工具。

### 跳过检测

- **问题：** 在已有工作树内创建嵌套工作树
- **修复：** 始终在创建任何东西之前运行第 0 步

### 跳过忽略验证

- **问题：** 工作树内容被跟踪，污染 git 状态
- **修复：** 始终在创建项目本地工作树之前使用 `git check-ignore`

### 假设目录位置

- **问题：** 创建不一致，违反项目约定
- **修复：** 遵循优先级：明确指令 > 已有项目本地目录 > 默认

### 在测试失败时继续

- **问题：** 无法区分新错误和已有问题
- **修复：** 报告失败，获取明确许可再继续

## 红旗

**绝不：**
- 当第 0 步检测到已有隔离时创建工作树
- 当你有原生工作树工具（如 `EnterWorktree`）时使用 `git worktree add`。这是第一错误——如果你有它，使用它。
- 通过直接跳到第 1b 步的 git 命令来跳过第 1a 步
- 在未验证被忽略的情况下创建工作树（项目本地）
- 跳过基线测试验证
- 在未询问的情况下在失败的测试上继续

**始终：**
- 首先运行第 0 步检测
- 优先使用原生工具而非 git 回退
- 遵循目录优先级：明确指令 > 已有项目本地目录 > 默认
- 验证项目本地目录被忽略
- 自动检测并运行项目设置
- 验证干净的测试基线
